## 1. Краткое резюме

Bilolidin — персональное портфолио full-stack разработчика из Кыргызстана: один сайт, который показывает проекты, кейсы и живую активность на GitHub и служит точкой контакта для нанимателей и клиентов.

Технически это **полностью статический сайт**: `next build` с `output: "export"` заранее рендерит 41 HTML-страницу в папку `out/`, которую раздаёт любой CDN — в продакшене Vercel. На сервере в момент запроса не выполняется ни одной строки кода: нет Serverless Functions, нет ISR, нет API-роутов, поэтому лимит Fluid Active CPU не расходуется вообще.

Сайт существует на трёх языках: английский — без префикса в URL (`/`, `/about`), русский и узбекский — под `/ru/...` и `/uz/...`. Контент проектов лежит в репозитории (реестр `src/data/projects.ts`), а данные GitHub — профиль, репозитории, языковая статистика, закреплённые репозитории — **запекаются в HTML на этапе сборки** и обновляются при следующем деплое.

README любого репозитория подтягивается не через сервер, а напрямую из браузера к `api.github.com` (у него разрешительный CORS), поэтому даже эта функция не требует бэкенда.

## 2. Проблема и цель

### Какую задачу решает

| Проблема | Решение в проекте |
|---|---|
| Нужна витрина работ для нанимателей и клиентов, а не список ссылок | Каталог курируемых проектов с ролями, тегами, кейс-стади и ссылками Live/Code |
| Аудитория говорит на трёх языках | Три локали (en / ru / uz) с локализованным контентом, включая описания карточек GitHub, и корректным SEO (canonical + hreflang) |
| Хостинг не должен стоить денег и жечь лимиты | Статический экспорт: раздача с CDN, 0 серверных функций, 0 Fluid Active CPU |
| Данные о проектах должны быть честными и не устаревать молча | GitHub как источник правды (pinned + repos) с детерминированным фолбэком на реестр проектов, если токена нет |
| Шеринг и индексация не должны быть ручной работой | OG-картинка, favicon, `sitemap.xml`, `robots.txt` и JSON-LD генерируются кодом на сборке |
| Сайт не должен ломаться при отсутствии секретов | Все обращения к GitHub обёрнуты в `allSettled`: без `GITHUB_USERNAME` сборка не падает, а рендерит понятное состояние (проверено) |

### Для кого

- **Нанимающий менеджер / рекрутер** — быстро понять уровень, стек и роль в проектах.
- **Потенциальный клиент** — увидеть кейсы и связаться (email, Telegram, Instagram, GitHub).
- **Коллега-разработчик** — посмотреть код и GitHub-активность.
- **Поисковые системы и соцсети** — получить корректные метаданные и превью для ссылки.

### Цель в измеримых терминах

Любой визит = статические файлы с CDN (нулевое серверное время); правка контента = один коммит в реестр данных + деплой; отсутствие переменных окружения не ломает публикацию.

**Секция GitHub** — «Selected work»: до 6 карточек с названием, локализованным описанием, языком, звёздами и форками; полоса распределения языков (топ-5 + «Other», затухающая прозрачность по позиции); список последней активности с относительными датами на языке страницы; кнопка «Open GitHub profile».

**Что важно знать про внешний вид:** это «тёмный» по духу дизайн с техно-эстетикой (mono-подписи, точечная сетка, тонкие линии), но он полностью адаптивный и корректно работает в светлой теме; анимации деликатные и уважают `prefers-reduced-motion`.

## 4. Как это работает (пользовательские сценарии)

### Сценарий 1: посетитель с лендинга до контакта

1. Открывает `/` — видит доступность, роль, стек и две кнопки.
2. Скроллит: стек → принципы → о себе → опыт → GitHub-секцию.
3. Кликает карточку проекта → страница проекта → кнопки «Открыть проект» / «Код».
4. Возвращается на главную и уходит в `/profile`, чтобы посмотреть все репозитории.
5. Открывает README интересного репозитория прямо на сайте (иконка документа).
6. Переходит в контакты: письмо (`mailto`) или Telegram.
7. Переключает язык на `/ru`, оставаясь на той же странице; переключает тему — выбор сохраняется.

### Сценарий 2: смена языка

1. Пользователь нажимает переключатель языка в шапке.
2. Сайт вычисляет текущий маршрут из URL, переносит query-строку и якорь, ведёт на тот же экран в следующей локали (en → ru → uz → en).
3. Метаданные страницы уже содержат canonical и альтернативы `hreflang` для всех трёх языков, поэтому поисковик связывает версии.

### Сценарий 3: смена темы

1. Клик по кнопке темы.
2. Атрибут `data-theme` на `<html>` меняется через View Transition (круговая волна из кнопки).
3. Значение пишется в `localStorage`; при следующем открытии сайта инлайн-скрипт в `<body>` ставит тему **до первой отрисовки** — вспышки неправильной темы нет. При переходах между страницами провайдер темы переустанавливает атрибут (иначе React мог его потерять).

### Сценарий 4: чтение README репозитория

1. На `/profile` пользователь нажимает иконку документа у репозитория.
2. Показывается skeleton-заглушка (во время загрузки).
3. Браузер запрашивает `api.github.com/repos/{owner}/{repo}/readme`; результат кешируется в состоянии — повторное открытие не делает запрос.
4. Markdown рендерится в модальном окне.
5. Если README нет — «У этого репозитория нет README»; если запрос не удался — «README не удалось загрузить».

### Сценарий 5: неизвестный URL

1. Пользователь попадает на несуществующий адрес.
2. CDN отдаёт статический `404.html` со статусом 404: та же тема, шрифты, локализованный текст, ссылка домой, `noindex`.

### Сценарий 6: ссылка в соцсети или поиске

1. Пользователь делится ссылкой на сайт.
2. В превью подтягивается сгенерированная на сборке OG-картинка 1200×630 (вордмарк, роль, градиентная линия) и метаданные OG/Twitter.
3. `sitemap.xml` со всеми локалями и `robots.txt` помогают индексации; JSON-LD (Person + WebSite) даёт поисковику структурированные данные.

### Что происходит «под капотом» при переходах

Переходы внутри сайта — клиентские (Next.js App Router): страница не перезагружается, вместо этого подгружается RSC-payload (`.txt`-файл из той же статики). Блоки секций появляются с мягкой анимацией при попадании в область видимости.

## 5. Архитектура и устройство

### Схема в двух режимах: сборка и запрос

```
СБОРКА (Node, один раз, при деплое)
  src/app/**/page.tsx ──► src/views/**  ──► src/components/**
        │                     │
        │                     ├─ src/data/projects.ts, home.ts, contact.ts
        │                     ├─ src/i18n/* (словари, localePath, metadata)
        │                     └─ src/lib/github.ts
        │                            ├─ REST  /users/{login}
        │                            ├─ REST  /users/{login}/repos ─► languageStats, recentRepos
        │                            └─ GraphQL pinnedItems ─► или фолбэк из projects.ts
        ▼
  out/ : 41 HTML + RSC-payload'ы (.txt) + _next/static + 404.html + icon +
         opengraph-image + robots.txt + sitemap.xml

ЗАПРОС В ПРОДАКШЕНЕ
  Браузер ──► CDN/Vercel (только статические файлы) ──► HTML со «запечёнными» данными
     │
     ├─ клиентская навигация ──► /<путь>/__next.*.txt (payload)
     ├─ клик по README ──► api.github.com (CORS) ──► react-markdown в диалоге
     └─ localStorage.theme ──► data-theme до первой отрисовки (инлайн-скрипт)

  Серверных функций, БД и фоновых процессов — нет.
```

### Слои кода

| Слой | Где | Ответственность |
|---|---|---|
| Маршруты | `src/app/(default)/**`, `src/app/[locale]/**` | Тонкие адаптеры: `params`, `generateStaticParams`, `generateMetadata`, делегирование во view |
| Тела страниц | `src/views/**` | Server Components: собрать данные, разложить по компонентам, отдать метаданные |
| Компоненты | `src/components/**` | Презентация: `layout` (шапка/подвал/тема/эффекты), `home`, `project(s)`, `profile`, `ui` (Radix+shadcn), `effects` |
| Данные | `src/data/**` | Реестр проектов и хелперы локализации/сопоставления с GitHub, контакты, данные главной |
| Локализация | `src/i18n/**` | Локали и хелперы путей, словари, метаданные (canonical/hreflang/OG) |
| Интеграции | `src/lib/**` | GitHub на сборке, GitHub в браузере, утилиты |
| Типы | `src/types/**` | Доменная модель `Project` и пр. |

### Два корневых layout-а — ключевая особенность

В проекте **нет** общего `src/app/layout.tsx`. Вместо него два независимых корневых дерева: `(default)` (английский, URL без префикса) и `[locale]` (ru/uz). Каждое рендерит свой `<html lang>`, свои метаданные и свой набор статических параметров. Оба дерева используют один и тот же каркас `SiteShell` и одни и те же тела из `src/views` — так контент существует в одном экземпляре, а локали остаются полностью статическими.

Побочный эффект: у несуществующего URL нет layout-цепочки, из которой Next.js собрал бы 404, поэтому включён режим `experimental.globalNotFound` и написан `src/app/global-not-found.tsx` — полноценный документ, который и становится `out/404.html`.

### URL-схема

| URL | Файл | Язык |
|---|---|---|
| `/`, `/about`, `/projects`, `/projects/<id>`, `/profile`, `/contact` | `src/app/(default)/…` | en |
| `/ru/…`, `/uz/…` | `src/app/[locale]/…` | ru / uz |
| `/en`, `/en/…` | — | 301 → `/`, `/…` (в `vercel.json` и локально в `scripts/serve.mjs`) |
| неизвестный | `out/404.html` | 404 |

### Инварианты статического экспорта

| Нельзя | Почему | Что используется вместо |
|---|---|---|
| `next/headers`, `cookies()` | нет серверного рантайма | локаль из сегмента URL / `usePathname()` |
| Server Actions, API-роуты | нет сервера для запросов | данные на сборке, README из браузера |
| middleware/proxy | не экспортируется | редиректы в `vercel.json` |
| Границы динамического рендеринга | нет ISR в рантайме | `force-static` для метаданных-роутов, фетчи на сборке |
| `next/image` с оптимизатором | оптимизатор — серверная функция | `images.unoptimized: true` |

| Что | Где менять | Комментарий |

| Цвета, радиус, свечение | `src/app/globals.css` → `:root` (светлая) и `:root[data-theme="dark"]` | светлая палитра висит на «голом» `:root`, поэтому страница читаема даже без JS |

| Иконка сайта и OG | `src/app/icon.tsx`, `src/app/opengraph-image.tsx` | это код, а не картинки: правка = пересборка |
| Анимации | `src/app/globals.css` (`typewriter`, `pulse-flow`, view-transition ripple), `src/components/ui/reveal.tsx`, `CursorGrid.tsx` | все уважают `prefers-reduced-motion` |

## 7. Данные и интеграции

### Что хранится в репозитории

| Источник | Содержимое |
|---|---|
| `src/data/projects.ts` | Реестр из 8 курируемых проектов: `id`, русское название/описание (базовый язык), теги, `githubUrl`, `liveUrl?`, роль, tier, обложка?, кейс? |
| `src/data/home.ts` | 4 принципа работы и тех-стек по группам (с иконками) |
| `src/data/contact.ts` | Email, GitHub, Telegram, Instagram |
| `src/data/site.ts` | Базовый URL сайта (из `NEXT_PUBLIC_SITE_URL`) — для canonical, OG, sitemap, JSON-LD |
| `src/i18n/{en,ru,uz}.ts` | Словари интерфейса, типизированные через `UiDictionary` |
| `public/manifest.json` | Манифест веб-приложения (иконки указывают на генерируемый `/icon`) |

Пример записи проекта (сокращённо):

```ts
{
  id: "prolab-academy",
  title: "PROlab Academy",
  description: "Платформа учебного центра…",   // базовый (русский) текст
  tags: ["Next.js", "TypeScript", "Supabase", "PostgreSQL", "RLS"],
  githubUrl: "https://github.com/bilolidin-dev/academy",
  liveUrl: "https://www.prolab-academy.site/",
  role: "Solo Developer",
  tier: "secondary",
  localized: { en: { description: "PROlab Academy educational-center platform…" } },
  customCaseStudy: { /* полный текст кейса для отдельной страницы */ },
}
```

### Что приходит извне

| Источник | Запрос | Когда | Что даёт |
|---|---|---|---|
| GitHub REST | `GET /users/{login}` | сборка | профиль (имя, аватар, био, счётчики) |
| GitHub REST | `GET /users/{login}/repos?per_page=100&sort=updated` | сборка | репозитории (форки отфильтрованы) → языковая статистика (топ-5 + Other) и 4 последних по обновлению |
| GitHub GraphQL | `pinnedItems(first: 6)` | сборка, только с токеном | закреплённые репозитории для «Selected work» |
| GitHub REST | `GET /repos/{owner}/{repo}/readme` | браузер, по клику | текст README для модального окна |

Ключевая связка: **курируемые проекты ↔ репозитории GitHub** сопоставляются по идентичности `owner/repo`, извлечённой из `githubUrl`. Благодаря этому карточка GitHub показывает локализованное описание проекта, а не сырой текст репозитория, а фолбэк «Selected work» строится из репозиториев, стоящих за проектами (в порядке реестра), если GraphQL недоступен.

### Переменные окружения (все — build-time)

| Переменная | Обязательна | Эффект отсутствия |
|---|---|---|
| `GITHUB_USERNAME` | для GitHub-секций | сборка проходит, секция GitHub показывает «данные не загрузились», профиль пуст |
| `GITHUB_TOKEN` | нет | REST работает анонимно (60 запросов/час на IP сборщика); закреплённые недоступны → фолбэк на курируемые проекты |
| `NEXT_PUBLIC_SITE_URL` | нет | canonical/OG/sitemap используют прод-URL Vercel по умолчанию |

Тонкости: при 401/403 с токеном запрос повторяется анонимно (токен — апгрейд лимита, а не необходимость); GraphQL-ошибка не роняет сборку; токен не попадает в клиентский бандл (не `NEXT_PUBLIC_`).

### Приватность

На сайте нет cookies, аналитики, трекеров и форм; в `localStorage` хранится только выбранная тема. Наружу (в GitHub) уходит только факт запроса README, инициированного самим пользователем.

## 8. Роли и доступы

| Субъект | Что может | Ограничения |
|---|---|---|
| Анонимный посетитель | Читать все страницы, переключать язык и тему, открывать внешние ссылки, читать README | Ничего не создаёт и не меняет; записи нет |
| Владелец / разработчик | Менять контент и код через git, деплоить (Vercel), управлять переменными окружения и кастомным доменом | Единственный, у кого есть доступ к репозиторию и аккаунту хостинга |

Аутентификации, авторизации, админ-панели, CMS и ролей пользователей в проекте нет — и не требуется, потому что нет ни пользовательских данных, ни мутаций. Единственный секрет — GitHub-токен, и он существует только в build-окружении.

Важно не путать: **RLS, JWT, роли учитель/ученик** — это описание кейса PROlab Academy (другой проект в портфолио), а не механизм этого сайта.

## 10. Ограничения и особенности

**Функциональные**

- Нет бэкенда, БД, форм, поиска по сайту, блога, комментариев, аналитики, авторизации — это осознанный выбор ради статической раздачи.
- Контакт = внешние каналы (`mailto`, Telegram, Instagram, GitHub), а не форма обратной связи.

**Данные**

- GitHub-данные запекаются на сборке: между деплоями они устаревают. Автоматической пересборки по расписанию пока нет — это ближайший план (§11).
- Базовый URL для canonical/hreflang/OG/sitemap берётся из `NEXT_PUBLIC_SITE_URL`, дефолт в коде — `https://www.bilolidin.dev`.
- Лимиты GitHub: 60 запросов/час на IP для анонимной сборки; столько же на IP посетителя для README.
- `/profile` отдаёт ~316 КБ HTML: весь список (33 репозитория) сериализуется в разметку для клиентского компонента — узкое место по весу.

**Инженерные**

- Любая попытка добавить серверную логику (API-роут, Server Action, middleware, ISR) сломает экспорт — сначала нужно менять модель хостинга (см. [ARCHITECTURE.md](ARCHITECTURE.md)).
- Нет CI, автотестов и мониторинга ошибок: регрессии ловятся только сборкой и ручной проверкой предпросмотра.
- `sitemap.xml` ставит `lastModified` = момент сборки для всех страниц (постоянно «свежая» дата).
- Часть проектов не имеет обложек (`image`) и полного кейса; единственный кастомный кейс — PROlab Academy.
- В корне лежат устаревшие документы (`AUDIT_REPORT.md`, `I18N_*.md`, `PROJECTS_REPORT.md`), ссылающиеся на старый аккаунт и старую структуру — не источник правды.

**Организационные**

- Проект ведёт один разработчик (соло): дизайнера, менеджера и процессов ревью нет. Аналитику и мониторинг решено не добавлять.
- Next.js выводит атрибут языковых альтернатив как `hrefLang` (camelCase) — для HTML и поисковиков это валидно, но строгие XML-валидаторы могут придираться.

## 11. Планы / будущее развитие

### Запланировано

**Автоматическая пересборка по расписанию.** Сейчас данные GitHub обновляются только при деплое, поэтому портфолио может показывать устаревшую активность. План — запускать сборку и публикацию по расписанию (воркфлоу в CI либо встроенный cron хостинга), не меняя архитектуру: сайт остаётся статическим, добавляется только внешний триггер. Результат: новый pinned-репозиторий или свежий коммит появляются на сайте в течение суток без ручных действий.

### Сознательно не планируется

**Аналитика и мониторинг ошибок.** Решение владельца — не добавлять: сайт сохраняет нулевой JS-оверхед и не собирает данные посетителей. Следствие: о клиентских сбоях узнаём только из сообщений пользователей.

### Backlog без решения

Идеи, зафиксированные при ревизии; приоритеты не определены.

| Кандидат | Зачем | Оценка |
|---|---|---|
| Облегчение `/profile` | Вес страницы ~316 КБ HTML из-за сериализации 33 репозиториев | Средняя: серверная пагинация, урезание полей или виртуализация |
| Smoke-тест артефакта в CI | Ловить нарушения инвариантов (серверные точки входа, пропавший `404.html`, hreflang) | Малая |
| Новые кейсы и обложки | Больше проектов с полноценным разбором; у части проектов нет `image` | Зависит от контента |
| Обновление/удаление старых отчётов | Чтобы агенты и люди не читали ложные данные (`AUDIT_REPORT.md` и др.) | Малая |
| Расширение языков | Схема словарей и префиксов масштабируется автоматически | Малая на инфраструктуре, большая на переводе |
